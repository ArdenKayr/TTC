# Правила проекта TTC

## Главное правило: у каждого элемента сценария есть подписанный смысл

**Появился новый элемент сценария — в том же изменении опиши, что он значит для
человека.** Элемент сценария — это всё, с чем сталкивается живой человек:

* кнопка (новая константа в классе `BTN` в `bot/texts.py`);
* команда (`Command("...")` или `CommandStart()` в `bot/routers/`);
* шаг формы, который ждёт от человека текст, фото или файл;
* сообщение, которое бот отправляет сам (сценарий, уведомление, напоминание);
* новый блок раздела, редактируемый через «🛠 Админство» → «📄 Разделы».

Смысл пишется в `docs/scenario-map.json` — это единственное место, где живёт
человеческое описание проекта. Новый узел добавляется в подходящую область
(`areas`) и заполняется целиком:

```json
{
  "id": "короткий_идентификатор",
  "trigger_kind": "reply_button",
  "trigger_ref": "BTN.НОВАЯ_КНОПКА",
  "where": "dm",
  "roles": ["admin", "superadmin", "owner"],
  "handler": "bot/routers/файл.py:имя_функции",
  "does": "Что происходит внутри бота, когда человек это нажал.",
  "shows": "Что человек видит на экране в ответ — своими словами.",
  "next": ["id_следующего_шага"],
  "db_reads": ["users"],
  "db_writes": [],
  "notifies": []
}
```

Что важно соблюсти:

* **`trigger_ref`, а не переписанная подпись.** Ссылка на константу `BTN.*`
  означает, что карта берёт текст кнопки прямо из кода: переименовали кнопку —
  карта показала новое имя сама. Литералом (`trigger_text`) описываются только
  команды и свободный ввод («любой текст на шаге ввода имени»).
* **`does` и `shows` — разные вещи.** `does` — что делает бот (проверил права,
  записал заявку, отправил админам). `shows` — что человек увидел на экране.
  Владелец проекта читает вторую строку, чтобы понять поведение без кода.
* **`next` связывает шаги.** Именно из этих ссылок строится визуальная схема.
  Узел без входящих и исходящих связей выглядит на схеме сиротой — если шаг
  куда-то ведёт, это надо указать.
* **`roles` — кто реально это увидит.** Роли берутся из `UserRole`; список
  перечисляет всех, кому элемент доступен, а не только минимальную роль.

Если элемент — редактируемый сценарий или блок «📄 Разделы», его ключ дополнительно
попадает в разделы `scenarios` / `slots` того же файла, с указанием узлов, в
которых человек это сообщение видит.

## Как проверить, что ничего не забыто

```
.venv\Scripts\python -m pytest tests/test_scenario_map.py
```

Тест сверяет карту с кодом в обе стороны: падает и когда в коде появился
элемент без описания, и когда в карте осталось описание того, чего в коде уже
нет. Это не формальность — именно он держит карту актуальной вместо дисциплины.

Посмотреть результат: двойной клик по `карта-сценариев.bat` в корне проекта —
пересобирает страницу из кода и открывает её в браузере.

## Второе правило: обновления выпускаются только по регламенту

Проект вышел в релиз 2 сентября 2026 года, у него есть живые пользователи.
Любое изменение, которое они увидят, выпускается по `docs/RELEASE_RULES.md` —
целиком, без выборочного применения. Коротко, шесть правил владельца:

1. **У обновления есть название** — номер и человеческое имя, файл
   `docs/releases/NN-slug.md`.
2. **Каждый пункт этих правил проверяется и подтверждается вслух** в конце
   работы: построчно, что именно сделано по каждому. Невыполненный пункт
   называется невыполненным, с причиной, — это единственный способ его
   пропустить.
3. **Страница обновления для участников** — HTML, текст копируется кнопкой и
   вставляется в Telegraph. Пишется как человек, а не как нейросеть: сухо,
   понятно неспециалисту, без лишних подробностей, о которых не просили.
   Каждый пункт — сначала суть в одну строку, затем что изменилось на экране.
4. **Отдельная такая же страница для админов и суперадминов** — с их
   функционалом.
5. **Вся документация и карта сценариев обновляются тем же изменением**
   (список файлов — в регламенте), проверка — `pytest`.
6. **Проверки до выкатки, присмотр после.** Отдельного тестового бота у
   проекта нет сознательно — не плодим вторые аккаунты, чаты и базы ради
   маленькой беты. Вместо него: `pytest` целиком, `ruff`, пересборка карты, а
   после выкатки — пройти изменённое живым человеком и присмотреть за
   журналом ошибок. Сломалось — чиним и выкатываем снова.

Собрать страницы обновления: двойной клик по `обновление.bat`.

## Остальное

Состояние проекта, архитектура и журнал работ — в `PROJECT.md` в корне.
Он же «пульт управления»: правки пользователя в нём — это задания на изменение
кода, а не текст, который надо откатить под текущее состояние.
