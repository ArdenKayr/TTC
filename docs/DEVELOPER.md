# TTC — техническая документация владельца

Этот документ объясняет, **как устроен проект изнутри**: откуда приходит информация, через какие этапы она проходит, где оседает и почему сделано именно так. Здесь нет кода и названий библиотек — только логика. Если нужен код: структура файлов описана в [PROJECT.md](../PROJECT.md) (раздел «Файлы и функции»), устройство базы — в [DATABASE.md](DATABASE.md).

## 1. Из чего состоит система

Четыре места, где «живёт» проект:

| Место | Что там | Кто им управляет |
|---|---|---|
| **Telegram** | Закрытая группа сообщества (с темами; вход только по ссылке от бота), закрытый админ-чат TTC_ADMIN (с темами), личные переписки людей с ботом @ttc_adm_bot | Telegram; бот действует через его API |
| **Боевой сервер** (VPS 45.91.238.177) | Три постоянно работающие программы-контейнера: сам бот, база данных PostgreSQL, быстрая память Redis | Мы |
| **GitHub** (приватный репозиторий ArdenKayr/TTC) | Код проекта и вся история его изменений | Мы |

Ключевая идея: **Telegram ничего не хранит для нас и ничего не решает**. Он только доставляет сообщения туда-сюда. Вся память — в базе на сервере, все решения — в коде бота.

## 2. Как информация попадает в бота

### 2.1. Опрос вместо ожидания

Бот **сам спрашивает** Telegram примерно раз в секунду: «что нового?» (это называется long polling). Telegram отдаёт пачку событий: кто-то написал боту в личку, нажал кнопку, отправил сообщение в группе, вступил в чат. Обратной схемы («Telegram сам стучится к нам») у нас нет — она требует домена и сертификата, а выгоды на нашем масштабе не даёт.

Из этого следует важное правило: **опрашивать Telegram может только один экземпляр бота**. Если запустить бота одновременно на сервере и на домашнем компьютере, они начнут «отнимать» события друг у друга, и Telegram будет рвать соединение обоим. Поэтому локальный бот остановлен, работает только серверный.

### 2.2. Конвейер: что происходит с каждым событием

Каждое событие проходит одинаковый путь из шести шагов:

```
Событие из Telegram
  → 1. Открывается подключение к базе (одно на событие; в конце — закрывается)
  → 2. По номеру Telegram-аккаунта из базы достаётся «кто это» (роль, имя, права)
  → 3. Проверка бана: если роль banned — человек получает отказ, дальше событие не идёт
  → 4. Выбор обработчика: бот смотрит, что это (команда? кнопка? текст на шаге анкеты?
       сообщение в группе?) и у кого какие права, и находит ровно один подходящий обработчик
  → 5. Обработчик проверяет формат ввода (та ли дата, не длинен ли текст) и зовёт «сервис» —
       участок кода, где живут правила проекта («что происходит при одобрении заявки»)
  → 6. Сервис пишет/читает базу и отправляет ответные сообщения через Telegram
```

Порядок выбора обработчика на шаге 4 не случаен: сначала проверяются админские обработчики (карточки заявок, панели), потом пользовательские (анкета, меню), в самом конце — «общие» (/start, кнопка «Кто мы?»). Поэтому одна и та же кнопка «✅ Принять» в разных карточках попадает в разные обработчики, и ничего не путается.

**Последний рубеж: подходящий обработчик находится всегда.** Раньше шаг 4 мог не найти никого — сообщение просто исчезало, и человек видел молчание, неотличимое от поломки. Теперь у каждой формы последним зарегистрирован обработчик без фильтров, а в самом конце последнего роутера — общий, на всю личку. Он объясняет, что пришло не то, и повторяет вопрос текущего шага; формулировку выбирает `bot/services/input_guard.py`, а сами фразы лежат в `bot/texts.py`.

Два правила, которые легко нарушить незаметно:

- **рубеж регистрируется последним** — обработчик без фильтров, поднятый выше шагов, перехватит саму анкету, и она перестанет заполняться;
- **рубеж есть у каждой формы** — иначе её неверный ввод провалится в общий рубеж и получит ответ «выберите кнопку в меню», хотя человек стоит посреди анкеты.

Оба правила держит `tests/test_input_guard.py`: он разбирает исходники роутеров и проверяет порядок регистрации, а не полагается на дисциплину. Группы это не касается — там свой сторож (`topic_guards`), и на обычные сообщения бот молчит намеренно.

### 2.3. Два вида «памяти о разговоре»

- **Шаг анкеты** (человек заполняет регистрацию, заявку, форму CRUD) хранится в **Redis** — быстрой памяти. Там лежит «человек X сейчас на шаге "дата рождения", уже ввёл имя и вуз». Если бот перезапустится — Redis всё помнит, человек продолжит с того же места.
- **Кнопки под сообщениями** несут данные **в самих себе**: в невидимой начинке кнопки «✅ Принять» зашит номер заявки. Поэтому админ может нажать кнопку в карточке недельной давности, после трёх перезапусков бота — и всё сработает: бот прочитает номер из кнопки и найдёт заявку в базе.

У начинки кнопки есть жёсткий лимит Telegram — 64 байта. Поэтому внутри кнопок никогда не лежат «данные» (имя, текст) — только короткие коды и номера, по которым всё достаётся из базы.

## 3. Где что хранится

### 3.1. PostgreSQL — постоянная память (15 таблиц)

Единственный источник правды. Группы таблиц:

- **Люди**: `users` (кто участник, роль, права) — запись появляется только после одобрения заявки, не при первом сообщении боту.
- **Заявки** (каждая подача — отдельная строка, история не переписывается): `registration_requests` (вступление), `university_requests` (новый вуз), `alias_suggestions` (вариант поиска вуза), `activity_requests` (мероприятие), `vote_requests` (голосование).
- **Справочники**: `universities` (вузы), `university_aliases` (варианты их названий), `permission_groups` (группы админских прав).
- **Живое**: `activities` (мероприятия, которые висят в Афише).
- **Репорты**: `reports` (жалоба с номером, статусом и тем, кто её ведёт) и `report_messages` (переписка админов с автором). Появились, когда репорт перестал быть разовым сообщением в чат.
- **Контент**: `content_blocks` — редактируемые тексты и файлы бота. Здесь же, под ключами с приставкой `scen_`, лежат отредактированные «сценарии» (сообщения-реакции бота).
- **Журналы** (только пополняются, никогда не правятся): `audit_log` (кто из админов что сделал), `error_log` (технические сбои).

Подробно каждая колонка — в [DATABASE.md](DATABASE.md).

Структура базы **версионируется**: у каждой правки структуры (новая таблица, новая колонка) есть номер (сейчас — 0014). При каждом запуске бот первым делом сверяет номер структуры базы со своим и, если база отстаёт, подтягивает её сам. Поэтому обновление кода никогда не требует ручных действий с базой.

### 3.2. Redis — быстрая память

Хранит только одно: **незавершённые диалоги** (на каком шаге анкеты/формы человек и что уже ввёл). Это черновики: их потеря неприятна (людям придётся начать анкету заново), но не страшна — поэтому Redis не бэкапится. Всё ценное из анкеты попадает в PostgreSQL в момент нажатия «✅ Отправить».

### 3.3. Telegram — хранилище файлов

Фото и документы (например, картинка в приветствии) физически лежат **на серверах Telegram**. У нас в базе хранится только `file_id` — «квитанция», по которой Telegram отдаёт файл. Поэтому файлы ничего не весят в нашей базе, но и живут ровно столько, сколько живёт бот-владелец квитанции (file_id другого бота нам не подойдёт).

### 3.4. Файл настроек .env

Живёт **вне git** (секреты в репозиторий не попадают — проверено по всей истории). Два разных файла: на компьютере (пароль базы простой, не важно) и на сервере (пароль боевой). Внутри: токен бота, номера чатов и тем, доступы к базе и Redis. Номера тем Telegram не сообщает через API — они выяснены вручную и вписаны в настройки; если пересоздать тему в группе, номер изменится, и его нужно поправить в .env на сервере и перезапустить бота.

`GROUP_CHAT_ID` — **число**, а не имя. Группа закрытая: публичного имени у неё нет, вступают только по ссылке от бота. Номера чата и темы бот называет сам: написать в нужной теме `/id` (отвечает только админам). Число, в отличие от имени, не меняется, если группу переименовать.

## 4. Потоки информации по сценариям

Самое главное в этом документе. Для каждого сценария: что вводит человек → что и куда записывается → кто получает уведомления → что происходит при решении.

### 4.1. Регистрация

1. Человек жмёт «📝 Регистрация». Шаги диалога (ник → вуз → группа → дата рождения) копятся **в Redis**.
2. Шаг вуза — поиск по справочнику `universities` + `university_aliases`; опечатки прощает база (поиск по триграммам — фрагментам слов). Три ветки:
   - вуз найден → дополнительно бот спросит, удобно ли искалось; «неудобно» рождает **отдельные заявки** на варианты поиска (`alias_suggestions`, до 5 штук);
   - вуза нет → человек заполняет **заявку на вуз** (название, до 5 сокращений, ссылка для проверки) — она уйдёт админам раньше самой регистрации;
   - «не учусь в вузе СПб» → вместо вуза человек пишет «о себе» (10–500 символов).
3. «✅ Отправить» — момент истины: всё из Redis переезжает в PostgreSQL строкой в `registration_requests` (вместе с «черновиком» — что человек вводил дословно), Redis очищается. В админ-чат, в тему «Заявки», уходит карточка с кнопками.
   - Если была заявка на вуз, карточка регистрации **придерживается**: сначала админы решают по вузу, и только потом приходит регистрация (с пометкой, чем кончилось дело с вузом).
4. **«✅ Принять»**: создаётся строка в `users` (человек «родился» для системы), у Telegram запрашивается **одноразовая ссылка** в группу (живёт 15 минут, впускает ровно одного — пересылать бесполезно), ссылка уходит человеку в личку, в карточке появляется «Принята — имя админа», в `audit_log` — запись.
   - Ссылки создаёт одна функция `registration_service.create_invite_link` — и здесь, и по кнопке «🔗 Ссылка на группу» в разделе «ℹ️ Информация». Кнопка появилась по жалобам: 15 минут мало, ссылку теряли, и человек с одобренной заявкой оставался за дверью. Перед выдачей бот спрашивает у Telegram, не в группе ли человек уже (`is_group_member`); если Telegram не ответил — ссылка всё равно выдаётся: отказать тому, кто снаружи, хуже, чем выдать лишнюю. Если два админа нажали одновременно — сработает первый, второй увидит «уже обработана» (защита на уровне базы: строка при решении блокируется).
5. **«❌ Отклонить»**: человеку — личка об отказе (решение — одно нажатие, причину бот не спрашивает); в заявке проставляется время, раньше которого новая попытка невозможна: после 1-го отказа — сразу, дальше 10 → 30 → 70 → 150… минут (каждый раз чуть больше, чем вдвое; потолок 72 часа). Формулу считает код по номеру попытки — админам ничего считать не надо.

### 4.2. Мероприятия и голосования

Две независимые анкеты из личных сообщений бота:

- **«📅 Мероприятие»**: название → описание → **картинка** → что нужно для проведения → организаторы (текст с @никами) → ссылка на план → ссылка на беседу → комментарий админам (пропустить можно только три последних шага). Строка в `activity_requests` → карточка в «Заявки» вместе с картинкой.
  - «Принять» → строка в `activities`, пост мероприятия публикуется в тему **Афиша**: картинка с карточкой в подписи. Подпись в Telegram — не длиннее 1024 символов, а описание бывает до 2000: тогда картинка уходит отдельным сообщением, а карточка следом за ней. Что именно получилось, запоминается в `afisha_is_caption` — при закрытии мероприятия правится либо подпись, либо текст, и перепутать нельзя: Telegram откажет, и закрытое мероприятие останется висеть активным. Номер сообщения с карточкой — в `afisha_message_id`. Автор получает роль «организатор» (только если был обычным пользователем) и личку.
- **«📊 Голосование»**: вопрос → варианты (одним сообщением, каждый с новой строки, 2–10 штук) → **тип опроса** (анонимный или с видимыми голосами). Строка в `vote_requests` (поле `is_anonymous`) → карточка в «Заявки», где тип показан админу: после публикации Telegram сменить его не даёт, только пересоздать опрос.
  - «Принять» → бот вешает **настоящий Telegram-опрос** в тему «Голосования» с выбранным типом, автору — личка.
- Закрытие: админ жмёт «🛠 Админство» → «📅 Мероприятия» → список активных мероприятий с кнопками «✅ Завершить» / «🚫 Отменить». Карточка в Афише помечается «Прошло»/«Отменено», организатору уходит личка, и если активных мероприятий у него не осталось — роль «организатор» снимается **автоматически** (админов, суперадминов и кастомных этот механизм не трогает никогда — защита зашита в код).

### 4.3. Репорт и вызов админов

- **Репорт** (кнопка «🐞 Репорт»): текст 5–2000 символов → строка в `reports` с номером и статусом → карточка с кнопками в тему **«Репорты»** админ-чата. Сохранение идёт **до** отправки карточки: не дошла карточка — репорт всё равно виден в очереди «🛠 Админство» → «🐞 Репорты». Дальше это переписка: решения админа (в работе / готово / отклонён) уходят автору сценариями `report_progress`, `report_done`, `report_declined`, свободный ответ — `report_reply`; ответ автора возвращается в тему репортов и в `report_messages`. Карточка перерисовывается по `card_message_id` при каждом изменении, чтобы в чате не оставалось живых кнопок на закрытом репорте.
- **Вызов** (/admin, @admin или @админ в любой теме группы): в «Репорты» падает «🆘 такой-то зовёт админов» со ссылкой на сообщение и кнопкой «🙋 Возьмусь». Первый нажавший вписывается в текст, кнопка исчезает — остальные видят, что вызов разобран.

### 4.4. Смена роли, бан и разбан

Смена роли (кнопки в карточке «Пользователи») делает четыре вещи: проверяет иерархию (см. ниже), меняет `current_role` в `users`, пишет в `audit_log` старое и новое значение — и **отправляет человеку личку с новым нижним меню**.

Последний пункт неочевиден и важен. Нижнее меню в Telegram — это не свойство пользователя, которое бот может «переключить»: оно приезжает прицепом к сообщению и живёт, пока его не заменит следующее сообщение с новой клавиатурой. Пока бот молчит, у человека остаётся та клавиатура, которую он получил последней. Поэтому назначение суперадмином без личного сообщения выглядело бы так: в базе роль новая, права работают, команды работают — а кнопки на экране старые, вплоть до «📝 Регистрация», если человек не писал боту с момента одобрения анкеты. То же правило действует при одобрении регистрации, бане и разбане.

Если личку доставить не удалось (человек не запускал бота или заблокировал его), это **не** считается ошибкой операции — роль сменилась. Но след остаётся в двух местах: «мягкая» запись в `error_log` с карточкой владельцу (§4.10) и предупреждение тому админу, который назначал. Меню у человека обновится само при первом /start.

Кнопка «🔨 Забанить» (после шага с причиной) делает четыре вещи: роль в `users` меняется на banned (старая роль запоминается), человек исключается из группы, ему уходит личка (текст настраивается в «Сценариях»), запись в `audit_log`. С этого момента конвейер (шаг 3, см. §2.2) отбивает любые его обращения к боту — заново зарегистрироваться с того же Telegram-аккаунта нельзя, потому что бан хранится в базе, а не «в чате». Кнопка «✅ Разбанить» возвращает **ту роль, что была до бана**.

Иерархия банов: админа банит только суперадмин или владелец, суперадмина — только владелец, владельца — никто.

### 4.5. Профиль и удаление аккаунта

«👤 Мой профиль» показывает данные из `users`; правки (ник, группа, дата рождения, «о себе») пишутся туда же, каждая — след в `audit_log`.

**«🗑 Удалить аккаунт»** (с подтверждением) устроено как «стереть личное, сохранить историю»: строка `users` и собственные нерешённые заявки удаляются; активные мероприятия человека отменяются (с пометкой в Афише); в журналах и уже решённых заявках ссылки на человека **зануляются** — сами записи остаются, но больше не указывают на конкретного человека. Человек исключается из группы. После этого можно зарегистрироваться заново с нуля.

### 4.6. Контент и сценарии — тексты без программиста

Два редактора с одним механизмом под капотом (таблица `content_blocks`):

- **«📄 Разделы»** — «страницы»: приветствие, «Кто мы?», «Инструкция: ссылка на статью», Правила, Документы, Обновления, «Стать организатором», «Стать админом», «Регламенты» (последняя видна только суперадминам). У блока есть текст и, по желанию, файл (фото/документ).
- **«🧩 Сценарии»** (панель Админства) — «реакции»: 22 сообщения, которые бот шлёт сам (одобрение/отказ заявок, смена роли, лички при бане и т.д.). Хранятся в той же таблице под ключами `scen_*`.

Правило надёжности: если блок/сценарий не заполнен (или заполнен с ошибкой в разметке) — бот показывает **встроенный текст из кода**. Сообщение уйдёт всегда, «сломать бота» правкой текста невозможно. Подстановки вида `{title}` бот заполняет сам; сценарий с непарными скобками просто не сохранится.

**Оформление и премиум-эмодзи.** Telegram присылает оформление отдельно от букв: сам текст плюс список пометок («с 0-го символа по 2-й — премиум-эмодзи №5368…», «с 10-го по 15-й — жирный»). Премиум-эмодзи — это именно такая пометка поверх обычного эмодзи-заменителя, а не отдельный символ. Раньше редакторы забирали из сообщения только буквы, поэтому пометки терялись: премиум-эмодзи вырождалась в обычную, жирный и ссылки пропадали. Теперь пометки переводятся обратно в HTML-теги (`<tg-emoji emoji-id="…">`, `<b>`, `<a href="…">`) — бот и так шлёт всё в режиме HTML, поэтому получатель видит ровно то, что админ набрал в Telegram. Побочные эффекты, оба полезные: обычные символы при этом экранируются (символ `<` в тексте больше не ломает отправку), а HTML-теги, набранные руками, теперь показываются как текст — оформлять надо средствами Telegram.

Отдельная защита в редакторе сценариев: если оформление попало **внутрь** подстановки (`{<b>title</b>}` вместо `<b>{title}</b>` — легко получить, выделив жирным слово без скобок), текст не принимается. Формально скобки парные и обычная проверка молчит, но имя подстановки при этом ломается, и человек получил бы сырое `{<b>title</b>}` вместо названия мероприятия.

Ограничение платформы: премиум-подписка нужна тому, кто отправляет, — но на ботов это не распространяется, и видят такие эмодзи все получатели, включая без премиума (проверено на живом боте).

### 4.7. CRUD — прямой доступ к базе из бота

Панель «🗄 CRUD» — таблица → список записей (страницами по 8) → карточка записи → правка любого поля / удаление / создание (в справочниках). Каждый ввод проверяется по типу колонки (число, дата ДД.ММ.ГГГГ, роль из списка, JSON; «-» очищает необязательное поле) — записать «мусор» в базу нельзя, бот объяснит, что не так. Удаление, за которое «цепляются» другие записи, база не пропустит — бот переведёт отказ на человеческий. Каждая операция — след в `audit_log` со старым и новым значением.

Защита от самоповышения: суперадмины видят таблицу `users` **только для чтения** — роли меняются только через панель «Пользователи», где иерархия проверяется кодом.

### 4.8. Обновления — рассылка всем

Владелец присылает текст (или фото/документ с подписью) → предпросмотр → «📢 Разослать всем». Происходят две вещи:
1. Запись с датой встаёт **сверху** раздела «Информация → Обновления»; старое содержимое остаётся ниже как архив (при переполнении лимита Telegram в 4096 символов хвост архива обрезается).
2. Бот идёт по всем зарегистрированным (кроме забаненных) и шлёт каждому личку — с паузой между отправками, чтобы не упереться во флуд-лимит Telegram (~30 сообщений/сек). Кто закрыл личку с ботом — просто пропускается. В конце владелец получает отчёт «доставлено X из Y».

### 4.9. Аудит и «Логи»

`audit_log` пишется **из сервисов** — в том же месте, где происходит само действие. Записывается: кто (или «система»), что сделал, над кем/чем, причина, детали (например, старая и новая роль), когда. Панель «📜 Логи» (только владелец) — это витрина над этим журналом: 7 тем (Ошибки / База данных / Контент и сценарии / Люди и роли / Мероприятия и голосования / Вузы / Всё подряд) × 4 периода (сутки / неделя / месяц / всё время), последние 25 записей по-русски.

### 4.10. Ошибки — «чёрный ящик» (и «мягкие сбои», которые не роняют бота)

Два независимых входа в один и тот же журнал `error_log` и одну и ту же карточку владельцу в личку:

- **Настоящий крэш.** Если любой обработчик падает с ошибкой, событие перехватывает **страховочный контур**: полная информация (какое событие, кто, какой чат, что человек ввёл, тип ошибки, полный технический след) пишется в базу, а владельцу немедленно уходит карточка с выжимкой — её достаточно переслать разработчику.
- **«Мягкий сбой».** Функция НЕ упала, но результат не тот, что задуман: не создалась инвайт-ссылка, не доставилась личка, не удалось исключить забаненного из группы, не встала карточка в Афишу. Раньше такие случаи в лучшем случае мелькали строкой в ответе решающему админу и терялись навсегда после закрытия чата; теперь каждый такой случай тоже пишется в `error_log` (с пометкой «⚠» вместо имени исключения — крэши и мягкие сбои визуально различимы) и владелец получает такую же карточку. Это отвечает на вопрос «что конкретно пошло не так у конкретного человека», даже когда код формально отработал без падения.

Оба пути работают на отдельном подключении к базе и сами обёрнуты в защиту: даже если сломается сама запись об ошибке, бот не упадёт. В карточке и в панели «Логи → Ошибки» человек теперь показывается по имени (если зарегистрирован), а не только номером аккаунта. Полные записи с трейсбеком — в CRUD → «Логи ошибок».

## 5. Роли и права: где что проверяется

Иерархия: **владелец → суперадмин → админ → организатор → пользователь**; отдельно «кастом» (набор модулей без полной роли) и «забанен».

Проверки происходят в **двух разных местах**, и это осознанно:

1. **На входе в обработчик** — быстрые проверки «эта кнопка/команда вообще для тебя?». Например, вся панель Админства открывается только суперадминам и владельцу; карточки заявок на регистрацию требуют модуль «Регистрация».
2. **Внутри сервисов** — проверки иерархии «а можешь ли ты сделать это с НИМ?». Например: суперадмин может забанить админа, но не другого суперадмина; снять суперадминство может только владелец. Эти правила живут в одном месте кода и работают одинаково, откуда бы действие ни пришло (панель, команда, CRUD).

Права «повседневной работы» (заявки, вузы, контент, модерация, мероприятия, репорты) разбиты на 6 **модулей**. Полные роли (админ/суперадмин/владелец) имеют все модули всегда; остальным модули выдаются лично или через **группу прав** (итог = модули группы + личные). Так можно сделать «модератора», который банит, но не трогает заявки.

## 6. Жизнь на боевом сервере

### 6.1. Что происходит при старте и падении

Порядок запуска: база данных и Redis стартуют первыми (бот ждёт их готовности) → контейнер бота сначала **подтягивает структуру базы** до своей версии → бот запускается и начинает опрос Telegram. Апдейты, накопившиеся за время простоя (перезапуск, деплой), при старте **дорабатываются**, а не выбрасываются — это осознанная настройка (см. врезку ниже), важная именно потому, что простой не бывает нулевым.

Если бот падает — контейнер перезапускается автоматически. Что при этом сохраняется:

| Что | Переживает перезапуск? | Почему |
|---|---|---|
| Участники, заявки, роли, контент, журналы | ✅ | PostgreSQL, данные на диске сервера |
| Незаконченные анкеты | ✅ | Redis работает отдельно от бота |
| Кнопки под старыми сообщениями | ✅ | Данные зашиты в самих кнопках |
| Сообщение/нажатие, случившееся, пока бот был недоступен | ✅ | Telegram придерживает апдейты для бота, пока никто их не забрал; при следующем старте бот их доработает |

**Что бот проверяет про группу при старте** (`main.resolve_group_chat_id`): открывает чат из `GROUP_CHAT_ID`, приводит его к числовому виду и спрашивает, может ли он приглашать в него по ссылке. Не открылся чат или нет права — в журнале появляется предупреждение. Заданное **именем** при неудаче выключается (слать по такому имени всё равно некуда), заданное **числом** — остаётся: число задано человеком явно, и разовый сбой связи не должен молча выключать группу до следующего перезапуска.

> **Найденный и исправленный баг (2026-08-05).** Группу сделали закрытой, её публичное имя исчезло — а в `GROUP_CHAT_ID` стояло именно имя. При старте бот не смог его открыть, обнулил настройку и **молча** остался без группы: ссылки на вступление не создавались, карточки в Афишу не уходили, охрана тем не работала. В журнале была ровно одна строка `Failed to resolve GROUP_CHAT_ID`, а узнали о поломке по жалобам людей, которые не могли войти в группу. Исправлено двумя вещами: число теперь тоже сверяется с Telegram (раньше принималось на веру — ошибка в нём не оставляла и той строки), и отдельно проверяется право приглашать по ссылке, потому что в закрытую группу другого входа нет.

> **Найденный и исправленный баг (2026-07-19).** Раньше при каждом старте бот явно просил Telegram отбросить всё, что накопилось за простой (`drop_pending_updates=True`) — так проще при частых перезапусках во время разработки, но опасно в бою: человек мог нажать «Отправить» анкету ровно в момент рестарта — заявка терялась насовсем, и **без единой записи в логах**, потому что апдейт не долетал до кода бота вообще (не было ни события, ни исключения — сработать и залогировать было просто нечему). Это и есть самое вероятное объяснение случая, когда заявка на регистрацию пропала без ответа и без ошибки в логе владельца. Настройка исправлена: теперь простой не приводит к потере действий пользователей.

### 6.2. Сетевые особенности этого VPS (важно!)

На сервере лежат два файла, которых **нет в git** — они решают проблемы конкретно этого дата-центра:

1. **Зеркала Docker-реестра** (в системных настройках Docker): Docker Hub отвечает отказом «429» российским серверным адресам — образы качаются через зеркала.
2. **IPv6 для контейнеров** (`docker-compose.override.yml` + `gai.conf` в папке проекта на сервере): api.telegram.org с этого сервера **недоступен по обычному IPv4** (соединение молча виснет), но отлично работает по IPv6. Контейнерам по умолчанию IPv6 не выдаётся — эти два файла включают его и заставляют предпочитать. **Если их удалить, бот перестанет отвечать без единой ошибки в логах** — он будет бесконечно ждать соединения.

**Замеры из контейнера бота (02.09.2026), если понадобится сверить:**

| Куда | Результат |
|---|---|
| IPv6 `2001:67c:4e8:f004::9` | соединение за 0,04 с — 4 попытки из 4 |
| IPv4 `149.154.166.110` | таймаут — 4 попытки из 4, ни одного успеха |

Настройка работает: пока IPv6 доступен, запросы идут за 100–300 мс. Но она лечит
не всё. Изредка IPv6 пропадает на десятки секунд — тогда остаётся мёртвый IPv4,
и запрос висит до конца таймаута. За неделю в журнале контейнера набирается около
70 строк про такие таймауты, и каждая означает, что кто-то из людей минуту смотрел
на молчащего бота.

Со стороны кода это закрыто в `bot/telegram_session.py`:

- **Протокол выбирается настройкой** `TELEGRAM_IP_FAMILY` (`auto` / `ipv6` / `ipv4`).
  На сервере стоит `ipv6`: запрос по заведомо мёртвому маршруту не уходит вовсе, и
  вместо минутного ожидания сразу получается отказ, который можно повторить.
- **Ожидание ограничено**: 5 секунд на соединение, 20 на весь запрос — вместо 60
  по умолчанию. Опроса событий это не касается: у long polling свой долгий таймаут.
- **Повтор при потерянной связи** — до трёх попыток с паузой в секунду. Повторяется
  только то, что заведомо не дошло: если ответ не вернулся, но запрос мог достичь
  Telegram, повтора не будет — иначе человек получил бы второе такое же сообщение.
  Отличаются эти случаи по времени (соединению отведено меньше, чем всему запросу).

**Измерить, а не гадать** — `scripts/net_watch.py`. Одна проверка обоих протоколов
изнутри контейнера бота: `docker exec ttc-bot-1 python /app/scripts/net_watch.py once`.
Строка дописывается в `/opt/ttc/data/netwatch.log` по расписанию (cron на хосте,
раз в минуту), сводка — `python3 /opt/ttc/scripts/net_watch.py report /opt/ttc/data/netwatch.log`.
Она отвечает на вопрос, ради которого всё затевалось: если IPv6 пропадает редко и
коротко — хватает настроек выше; если лежит минутами — нужен свой прокси.

### 6.3. Как выкатить обновление

С компьютера владельца, двойным кликом по `бой-выкатить.bat`. Внутри: запаковать код → скопировать на сервер → пересобрать и перезапустить контейнер бота. База и Redis при этом не перезапускаются, структура базы подтянется сама. Простой — секунды.

Скрипт (`scripts/deploy.py`) заодно не даёт выкатить лишнего: останавливается, если есть несохранённые изменения (на сервер уезжает только то, что в git), прогоняет тесты и просит подтвердить выкатку словом.

Отдельного тестового бота у проекта нет — это осознанное решение владельца: для беты на несколько десятков человек вторые аккаунт, чаты и база не окупаются. Вместо него проверки до выкатки и присмотр за журналом ошибок после (порядок — [docs/RELEASE_RULES.md](RELEASE_RULES.md)).

## 7. Ограничения Telegram, встроенные в проект

Эти цифры — не наши прихоти, а лимиты платформы; код спроектирован вокруг них:

| Лимит Telegram | Как учтено |
|---|---|
| Сообщение ≤ 4096 символов, подпись к файлу ≤ 1024 | Карточки CRUD и архив «Обновлений» обрезаются; длинные логи режутся до 25 записей |
| Начинка кнопки ≤ 64 байта | В кнопках только короткие коды, данные достаются из базы |
| ~30 сообщений в секунду на бота | Рассылка идёт с паузами |
| Опрос: вопрос ≤ 300, вариант ≤ 100, вариантов 2–10 | Проверки в анкете голосования |
| Бот не может написать первым | Все лички уходят только тем, кто когда-то писал боту; закрывшие личку молча пропускаются |
| Ответить на нажатие кнопки можно лишь несколько секунд | Нажатие подтверждается **до** работы (`bot/routers/admin/review_ui.py`), итог показывается в самой карточке. Иначе долгий разбор заканчивается ошибкой «query is too old», хотя решение уже принято |
| Создателя группы нельзя из неё исключить | Бан в боте срабатывает всегда, а отказ Telegram распознаётся и объясняется словами (`bot/services/group_service.py`) — вместо тревоги о поломке, которой нет |
| Бот не может узнать человека по @нику | Поиск людей в панелях работает только по зарегистрированным (они есть в базе) |
| file_id принадлежит боту | Файлы контента нельзя «перенести» другому боту — только перезалить |

## 8. Если что-то сломалось: порядок диагностики

1. **Бот молчит у всех** → зайти на сервер, посмотреть статус контейнеров и хвост лога бота (команды — в PROJECT.md). Нет «Run polling» — смотреть §6.2 (сеть) и .env.
2. **Бот отвечает, но какая-то функция даёт сбой** → у владельца в личке уже лежит карточка ошибки (§4.10); переслать её разработчику. Полная версия — CRUD → «Логи ошибок».
3. **«Кто это сделал и когда?»** → панель «Логи» по теме, либо CRUD → «Журнал действий».
4. **Человек говорит «мне не пришло сообщение»** → чаще всего он закрыл личку с ботом (Telegram запрещает боту писать первым, см. §7); рассылка его молча пропустила.
5. **Кнопка в старой карточке «не работает»** → заявка уже решена другим админом (это штатно, бот так и отвечает) — история в аудите.
