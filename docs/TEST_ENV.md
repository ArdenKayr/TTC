# Тестовый контур — где обновления щупают до боя

Правило 6 регламента обновлений: сначала тест, потом бой. Здесь описано, что
такое «тест», как его завести один раз и как им пользоваться дальше.

## Что это такое

**Второй бот, полностью отдельный от боевого.** У него своя база, свой Redis,
свои чаты и свои участники. Что бы тестировщики в нём ни сломали, боевого
сообщества это не касается: там другие данные и другой бот.

Живёт он на том же сервере, в соседней папке:

| | Боевой | Тестовый |
|---|---|---|
| Папка на сервере | `/opt/ttc` | `/opt/ttc-test` |
| Бот в Telegram | боевой | второй, отдельный |
| Контейнеры | `ttc-bot-1`, `ttc-postgres-1`, `ttc-redis-1` | `ttc-test-bot-1`, `ttc-test-postgres-1`, `ttc-test-redis-1` |
| База | том `ttc_postgres_data` | том `ttc-test_postgres_data` |
| Чаты | боевая группа и чат админов | тестовые группа и чат админов |
| Кто пользуется | участники сообщества | тестировщики |

Отдельный сервер не нужен, и вот почему. Docker Compose берёт имя проекта из
имени папки, а вместе с именем расходятся **все** имена контейнеров, сетей и
томов. Поэтому две папки — это два независимых хозяйства на одной машине,
которые ничего друг о друге не знают. Файлы проекта одинаковые, различаются
только `.env`. Ресурсов хватает с запасом: второй стек — это ещё около 300 МБ
памяти при 4 ГБ на сервере.

**Защита от самой дорогой ошибки встроена в код.** В тестовом `.env` стоит
`ENV_NAME=test`. С этой пометкой бот при запуске проверяет, не подсунули ли ему
боевые чаты, и если да — отказывается стартовать (`bot/config.py`). Ошибиться
файлом легко, а тестовый бот — такой же админ с правом удалять сообщения:
в боевой группе он начал бы наводить свои порядки.

## Что завести один раз

Это делается руками и только владельцем — у Claude нет доступа ни к
@BotFather, ни к вашим чатам.

### 1. Второй бот

1. В Telegram откройте **@BotFather** → `/newbot`.
2. Имя — например `ТТС (тест)`, адрес — например `ttc_beta_bot`. Пусть по
   названию сразу видно, что бот тестовый: тестировщики не должны их путать.
3. Скопируйте токен — он понадобится в пункте 3.
4. Там же: **Bot Settings → Group Privacy → Turn off**. Без этого бот не видит
   сообщений в группе, и половина проверок работать не будет.

### 2. Тестовые чаты

Нужны два, оба — супергруппы с включёнными темами (Topics):

- **Тестовая группа сообщества.** Темы: «Объявления», «Афиша», «Голосование»,
  «Флуд». Бот — админ с правами: удаление сообщений, бан, приглашения,
  управление темами.
- **Тестовый чат админов.** Темы: «Заявки», «Репорты». Бот — админ с правом
  удаления сообщений.

**Как узнать номера.** Откройте любое сообщение в теме → «Копировать ссылку».
Получится вида `t.me/c/1234567890/5/17`, где `1234567890` — номер чата, а `5` —
номер темы. В настройках чат пишется как `-100` + номер: `-1001234567890`.

### 3. Настройки на сервере

**Папка `/opt/ttc-test` уже создана, и всё, что не хранится в git, туда уже
положено** (3 августа 2026): `gai.conf`, свой `docker-compose.override.yml` и
образец настроек `.env.example`. Осталось заполнить сам `.env`:

```bash
ssh -i ~/.ssh/ttc_vps root@45.91.238.177
cp /opt/ttc-test/.env.example /opt/ttc-test/.env
nano /opt/ttc-test/.env
```

В `.env` тестового контура не должно остаться ни одного боевого значения:
другой токен, другие чаты, другой пароль базы.

Зачем эти файлы вообще нужны: `docker-compose.override.yml` и `gai.conf`
включают IPv6 — с этого сервера api.telegram.org по IPv4 недоступен, и без них
бот молча виснет на старте (см. «Особенности сети сервера» в `PROJECT.md`).
У тестового override **своя подсеть IPv6** (`fd12:3456:789b::/64` вместо
боевой `...789a::/64`): две сети с одинаковой подсетью Docker создать не даст,
и второй стек просто не поднялся бы.

### 4. Первый запуск

С компьютера — двойной клик по **`тест-выкатить.bat`**. Дальше на сервере:

```bash
cd /opt/ttc-test
docker compose logs -f bot     # ждём "ТЕСТОВЫЙ КОНТУР" и "Start polling"
docker compose run --rm bot python -m scripts.bootstrap_admin --tg-id <ваш_id> --name "Имя"
docker compose run --rm bot python -m scripts.seed_universities data/universities.csv
```

Первая строка в журнале должна быть про тестовый контур. Если её нет — в `.env`
не проставлен `ENV_NAME=test`, и вы смотрите на боевого бота.

## Как выкатывать обновления

1. **`тест-выкатить.bat`** — текущий коммит уезжает в тестовый контур. Перед
   отправкой прогоняются тесты и проверяется, что контур вообще настроен
   (есть папка и `.env`), а на сервере остаётся отметка: какой коммит выкачен
   и когда.
2. Тестировщики проходят проверки обновления (список — в файле обновления,
   `docs/releases/`).
3. Нашли ошибку — чиним, повторяем пункт 1.
4. **`бой-выкатить.bat`** — на боевой сервер. Скрипт сверяет коммит с отметкой
   из тестового контура: если на бой едет не то, что тестировали, он
   останавливается и говорит, чем именно отличается.

Обойти проверку можно (`python -m scripts.deploy prod --force`), но это
осознанное нарушение правила 6, и скрипт скажет об этом вслух.

## Что проверяют тестировщики

Общий круг для любого обновления — то, что ломается чаще всего:

1. **Новичок.** `/start` → регистрация целиком → заявка приходит в тестовый чат
   админов → одобрение → меню участника, ссылка-приглашение работает.
2. **Меню участника.** Каждая кнопка что-то показывает и возвращает назад.
3. **Мероприятие.** Заявка → одобрение → карточка в «Афише» → завершение.
4. **Голосование.** Создание, голос, публикация итогов.
5. **Админская панель.** Каждый раздел открывается; у админа с урезанными
   правами лишних разделов не видно.
6. **Модерация.** Бан с причиной, разбан, смена роли.
7. **Порядок в группе.** Сообщение в «Объявлениях» и «Афише» удаляется, вызов
   админов долетает в чат админов.

Плюс то, что менялось в самом обновлении, — этот список ведётся в файле
обновления.

## Полезные команды

```bash
cd /opt/ttc-test
docker compose logs -f bot            # журнал
docker compose restart bot            # перезапустить
docker compose ps                     # что запущено
docker compose exec postgres psql -U ttc -d ttc   # заглянуть в базу
```

**Начать тесты с чистого листа** (удаляет ВСЕ тестовые данные — участников,
заявки, мероприятия; боевых данных не касается, но отменить это нельзя):

```bash
cd /opt/ttc-test && docker compose down -v && docker compose up -d --build
```

После этого первого админа и список вузов нужно завести заново — пункт 4.

## Чего тестовый контур не заменяет

- **Сервер общий.** Если ляжет машина, лягут оба бота. Это плата за простоту;
  для беты приемлемо.
- **Данные не боевые.** Нагрузки живого сообщества здесь нет — тестируется
  поведение, а не производительность.
- **Автотесты никуда не деваются.** `pytest` проверяет код, тестовый контур —
  живого бота. Одно не заменяет другое.
